# Hotel Supplier Aggregator

- 여러 외부 숙박 상품 공급사의 재고와 요금을 하나의 플랫폼에서 통합해 보여주는 백엔드 시스템입니다. 

## 구현 목적 
- 숙박 플랫폼은 고객에게 정확한 숙소 정보를 제공해야 합니다.
- 공급사마다 상품을 표현하는 방식이 서로 달라(가격 산정 기준, 식별자 체계 등) 이를 그대로 노출하면 고객이 일관된 형태로 상품을 비교할 수 있습니다.

## 구현 목표 
- **"고객에게 일관된 정보를 정확하게 제공"** 하기 위해, 사전에 다른 형식의 공급사 응답을 표준 숙박 상품 모델로 정규화하고, 여러 공급사를 동시에 조회해 하나의 통합된 검색 결과로 병합하는 것을 목표로 합니다.
- **개인 학습 목표**: 
    - 이종 시스템 통합 설계 감각 : 실무에서는 외부 API를 여러 개 붙이는 일은 자주 일어나며, 정답이 없는 상황에서 무엇을 표준으로 삼고 무엇을 버릴지 판단하고 근거를 남기며 도메인을 빠르게 흡수하고자 합니다.
    - 비동기/병렬 처리 및 장애 격리 익히기 : 외부 서비스를 여러개 호출했을 시 우리 서비스에 장애가 전파되지 않기 위해 타임아웃, 부분 실패, 실패 판정 통일 같은 것을 직접 구현해보며 방어적 설계 습관을 갖추도록 합니다.
    - 어뎁터 패턴 사용: 우리 도메인이 외부 형식에 묶이지 않고 경계를 두는 경험을 함으로써 디자인 패턴 설계를 경험합니다.
    - 문서화 습관: 지속해서 판단 근거, 회고 등 히스토리를 남기며 문서화를 정교하게 하는 방법을 터득합니다.

## 주요 기능
- 서로 다른 형식의 외부 공급사 응답을 하나의 표준 숙박 상품 모델로 정규화한다.
- 날짜·인원 조건으로 여러 공급사를 동시에(병렬) 조회하는 통합 검색 API
- 공급사 코드와 내부 식별자를 매핑해, 지역 검색을 지원하지 않는 공급사 API를 조회 가능한 형태로 변환
- 일부 공급사 장애·무응답 시에도 나머지 공급사 결과로 정상 응답하는 부분 실패 허용 
- 신규 공급사 추가 시 변경 범위를 최소화하는 어댑터 계층 분리

## 실행 방법

### 요구 사항
- JDK 21+
- (Gradle Wrapper 포함되어 있어 별도 설치 불필요)

### 빌드 및 실행
```bash
./gradlew clean build
./gradlew bootRun
```

### Mock Supplier 서버
```bash
# 예: 9090 포트에서 Mock Supplier 기동
./gradlew :mock-supplier:bootRun
```

### 장애 모드 전환 (Mock 조작)
```bash
curl -X POST 'http://localhost:9090/control/a/mode?value=no-response'   # Supplier A 무응답
curl -X POST 'http://localhost:9090/control/b/mode?value=error'         # Supplier B 장애 (200+E503)
curl -X POST 'http://localhost:9090/control/a/mode?value=normal'        # 정상으로 복귀
```

### 통합 검색 API 호출 예시
```bash
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
```

### DB 콘솔 (H2 사용)
```
http://localhost:8080/h2-console
```

## 핵심 설계 결정

### 1. 표준 숙박 상품 모델

| 개념 | 표준 단위 |
|---|---|
| 숙소 | 물리적 시설 1곳 = 레코드 1개 |
| 객실 타입 | 숙소 내 객실 타입 1개 = 레코드 1개 (개별 물리 객실 아님) |
| 요금 | 요청한 숙박 기간 전체의 세금 포함 총액 |
| 재고 | 날짜별 잔여 객실 수 |

#### 1. 요금을 "기간 전체 총액" 단위로 잡은 이유
- 한 공급사는 날짜별로 요금을 쪼개서 제공하지만, 다른 공급사는 요청 기간 전체의 총액만 제공하고 날짜별 분해값을 주지 않는다. 
- 날짜별 단위를 표준으로 삼으면 후자의 데이터를 채울 방법이 없으므로, 양쪽 공급사 데이터를 모두 손실 없이 수용할 수 있는 "기간 전체 총액" 단위를 표준으로 선택했다.

#### 2. 요금을 세금 포함 기준으로 통일한 이유
- 한 공급사는 세금이 포함된 총액만 제공하고 세금 금액을 별도로 알려주지 않는다. 따라서 세금별도 기준을 표준으로 삼으면 해당 공급사의 데이터를 역산할 수 없다 (부가세 외에 다른 항목이 섞여 있을 가능성을 배제할 수 없어, 일률적인 세율 가정으로 역산하는 것은 부정확할 위험이 있다고 판단했다). 
- 반면 세금포함 기준은 두 공급사 데이터를 모두 손실 없이 채울 수 있고, 고객이 최종적으로 지불하는 금액 기준으로 비교할 수 있어 사용자 경험 측면에서도 자연스럽다.

#### 3. 재고를 날짜별 단위로 잡은 이유
- 두 공급사 모두 날짜별 잔여 객실 수를 제공하므로, 별도 가공 없이 표준 모델에 그대로 반영할 수 있다.

#### 4. 예약 가능 여부 판정 기준
- 연박(N박) 조회 시, 요청 기간 중 하루라도 잔여 객실 수가 0이면 해당 객실 타입은 예약 불가로 판정한다. 
- 모든 날짜에 방이 있어야 실제로 예약 가능한 상품이라는 게 고객 입장에서 의미가 있다고 판단했기 때문이다. 
- 예약 가능한 경우의 노출 객실 수는 요청 기간 중 최소 잔여 객실 수로 표시한다 (기간 전체에 걸쳐 보장되는 값이기 때문).

#### 5. 버린 정보
- 한 공급사가 제공하는 날짜별 세금 상세 내역(1박당 세금 별도 금액)은 표준 모델에서 버렸다. 
- 요금을 기간 전체 세금포함 총액 단위로 통일하면서, 날짜별 세부 분해는 검색 결과 비교에 필수적이지 않다고 판단했기 때문이다.

#### 6. 조식 포함 여부
- 요금과 별개의 boolean 속성으로 표준 모델에 유지한다. 
- 같은 객실 타입이라도 공급사마다 조식 포함 여부가 달라 요금 차이의 원인이 될 수 있으므로, 요금만 비교하면 오해를 살 수 있어 반드시 함께 노출해야 한다고 판단했다.

#### 2. 공급사 코드 ↔ 내부 식별자 매핑
#### 1. 매핑 주기
앱 기동 시 1회 생성한다. 공급사의 전체 상품 목록은 자주 바뀌지 않는 정적 정보인 반면, 재고·요금은 검색 시점마다 실시간으로 조회하는 방식으로 성격 차이를 반영했다. (주기적 갱신이 더 적절할 수 있다는 점은 인지하고 있으며, 갱신 로직을 호출부와 분리해 추후 스케줄러로 확장 가능한 구조로 설계했다.)
#### 2. 객실 타입 코드
- 소속 숙소 안에서만 유일하므로, 매핑 키에는 숙소 코드를 함께 포함시켰다.
#### 3. 동일한 공급사 상품
- 재조회해도 항상 같은 내부 식별자로 매핑되도록 했다 (기존 매핑이 있으면 재사용, 없을 때만 새로 생성).
- 서로 다른 공급사가 같은 물리적 숙소를 취급하더라도, 기본적으로는 별개의 내부 식별자를 가진다. 이를 하나로 합치는 중복 상품 병합은 선택 구현 항목으로 분리했다.
#### 4. 매핑 생성 중 일부 공급사 조회가 실패할 경우
- 실패할 경우에도 앱은 정상 기동** 하며, 성공한 공급사만 매핑을 채운다. 외부 API 장애가 서비스 전체를 막아서는 안 된다고 판단했기 때문이다. (자세한 스키마와 근거는 `docs/DESIGN.md` 참고)

### 3. Supplier 연동 어댑터
- Supplier별 요청/응답 형식이 도메인 계층으로 새어 나가지 않도록 어떻게 경계를 뒀는지
- 신규 Supplier 추가 시 무엇을 고쳐야 하는지

### 4. 통합 검색 API
- 예약 가능 객실 수를 어떻게 판정했는지 (0이면 예약 불가 등)
- 예약 불가 상품을 응답에서 뺄지 0으로 노출할지, 그 이유
- 숙소 코드가 50개를 초과할 경우 처리 방향 (설계만 했다면 그 내용)

### 5. 연동 견고성
- 타임아웃 값을 왜 그렇게 정했는지
- 부분 실패를 어떻게 허용했는지 (한쪽 Supplier 실패해도 응답 가능한 구조)
- Supplier B의 HTTP 200 + resultCode 실패를 A의 4xx/5xx와 어떻게 동일하게 취급했는지

### 6. (선택 구현 시) 추가 설계
- 재시도 정책 / 서킷 브레이커 / 캐시 전략 / 정규화 실패 데이터 격리 / 중복 상품 병합 / 통화 처리 / 예약 대행 흐름 중 진행한 항목만 작성
