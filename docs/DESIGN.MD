## 1. 숙박 상품 통합 모델 설계

### 단위 정의
| 개념 | 자사 표준 단위 |
|---|---|
| 숙소 (Stay) | 물리적 시설 1곳 = 레코드 1개 |
| 객실 타입 (RoomType) | 숙소 내 객실 타입 1개 = 레코드 1개 (개별 물리 객실 아님) |
| 요금 (Price) | 요청한 숙박 기간 전체의 세금 포함(gross) 총액 |
| 재고 (Inventory) | 날짜별 잔여 객실 수 |

### 필드별 판단 (근거)
- **요금**: 한 공급사는 날짜별로 요금을 쪼개서 제공하고, 다른 공급사는 기간 전체 총액만 제공하며 날짜별 분해값을 주지 않는다. 날짜별 단위를 표준으로 삼으면 후자의 데이터를 채울 수 없으므로, 양쪽을 모두 손실 없이 수용할 수 있는 "기간 전체 총액" 단위를 표준으로 선택했다.
- **세금 기준**: 한 공급사는 세금 포함 총액만 제공하고 세금 금액을 별도로 알려주지 않는다. 세금별도를 표준으로 삼으면 해당 공급사 데이터를 역산할 수 없고, 세금 구성(부가세만인지 다른 항목이 섞였는지)을 스펙만으로 단정할 수 없어 임의 역산은 부정확할 위험이 있다고 판단했다. 세금포함 기준은 양쪽 데이터를 모두 채울 수 있고, 고객이 최종 지불하는 금액 기준 비교가 가능하다.
- **재고**: 두 공급사 모두 날짜별 잔여 객실 수를 제공하므로 그대로 표준 모델에 반영했다.
- **조식 포함 여부**: 요금과 별개의 boolean 속성으로 유지한다. 같은 객실 타입이라도 공급사마다 조식 포함 여부가 달라 요금 차이의 원인이 될 수 있으므로, 요금만 비교하면 오해를 살 수 있다.
- **통화**: 두 공급사 모두 통화 코드를 함께 제공하므로, 금액과 통화를 하나의 값(Money)으로 묶어 표준 모델에 반영했다.
### 버린 정보
- 한 공급사가 제공하는 날짜별 세금 상세 내역(1박당 세금 별도 금액)은 표준 모델에서 버렸다. 요금을 기간 전체 세금포함 총액 단위로 통일하면서, 날짜별 세부 분해는 검색 결과 비교에 필수적이지 않다고 판단했기 때문이다.
- 서로 다른 공급사가 같은 물리적 숙소를 취급하는 경우, 이를 자동으로 식별해 하나로 합치는 기능은 구현하지 않았다 (공통 식별 키가 없어 정답이 없는 문제이며, 중복 상품 병합은 선택 구현 항목으로 분리했다).

## 2. 공급사 코드 ↔ 내부 식별자 매핑

### DB 스키마 (초안)
```
stay_mapping
  - internal_stay_id (PK)
  - supplier_code (예: SUPPLIER_A, SUPPLIER_B)
  - supplier_hotel_code
  - stay_name
 
room_type_mapping
  - internal_room_type_id (PK)
  - internal_stay_id (FK)
  - supplier_code
  - supplier_hotel_code   -- 객실 타입 코드가 숙소 안에서만 유일하므로 함께 필요
  - supplier_room_type_code
  - room_type_name
```

### 매핑 갱신 시점
- 선택: 앱 기동 시 1회
- 근거: 공급사의 전체 상품 목록은 자주 바뀌지 않는 정적 정보이므로, 검색 요청마다 재조회할 필요가 없다. 매번 조회하면 불필요한 API 호출과 응답 지연이 발생해, 안내문이 강조한 "①과 ②의 성격 차이 반영"과 반대 방향이 된다.
- 한계 및 확장 방향: 앱이 재기동되지 않는 한 신규 숙소가 반영되지 않는다는 한계가 있다. 실제 서비스라면 주기적 스케줄러(예: 매일 새벽 1회) 갱신이 더 적절하지만, 과제 범위상 우선순위를 낮췄다. 다만 매핑 생성 로직(refreshMapping)을 호출 시점과 분리해서 설계해, `@Scheduled` 메서드 하나만 추가하면 손쉽게 확장 가능한 구조로 만들었다.
### 숙소 목록(①) vs 재고·요금(②) 성격 차이 반영
- ①은 자주 안 바뀜 → 앱 기동 시 1회 호출해 DB에 저장, 이후 재사용
- ②는 매번 바뀜 → 검색 요청이 들어올 때마다 실시간으로 호출, DB에 저장하지 않음
### 매핑 생성 실패 시 처리
- 일부 공급사의 숙소 목록 조회(①)가 실패해도 앱은 정상 기동시킨다. 외부 API 장애가 서비스 전체 기동을 막아서는 안 된다고 판단했기 때문이다.
- 실패한 공급사는 매핑을 채우지 않고, 성공한 공급사만 매핑을 채운다. 이후 검색 시에는 매핑이 있는 공급사만 조회 대상이 된다.
- 모든 공급사가 실패하면 자사 직접 등록 숙소만으로 서비스한다.
- 실패는 로그로 원인을 남기고, 알림(Slack/메일 등)을 고려한다. (로그를 별도 스키마로 저장할지, 애플리케이션 로그만으로 충분할지는 구현 범위에 따라 결정 — 시간 여력에 따라 단순화 가능)
### 확장성 (숙소가 수천 개일 때)
- 재고·요금 조회(②)는 한 번에 최대 50개 숙소 코드까지만 받으므로, 보유 숙소가 그 이상이면 50개 단위로 배치를 나눠 여러 번 호출해야 한다.
